# 게시글 편집 충돌 처리

## API 계약

목록·상세 응답의 `version`은 클라이언트가 읽은 게시글 편집 버전입니다.
수정 요청은 제목·본문과 그 버전을 함께 전달합니다.

```json
{"title":"수정한 제목","content":"수정한 본문","version":0}
```

A와 B가 version 0을 읽었을 때 A의 내용 변경이 먼저 커밋되면 DB 버전은 1이 됩니다.
B가 version 0으로 수정하면 409·CONFLICT를 반환하고 A의 변경은 보존합니다.
B는 최신 내용을 다시 조회하고 자신의 변경과 비교한 뒤 새 버전으로 요청해야 합니다.
서버는 버전을 바꿔 자동 재시도하지 않습니다. 이전 본문을 최신 버전으로 덮어쓰면
방지하려던 변경 유실이 다시 발생하기 때문입니다.

| 상황 | 응답 |
| --- | --- |
| version 누락·null·음수 | 400 VALIDATION_FAILED와 version 필드 오류 |
| 소수·long 범위 초과 등 역직렬화 불가능한 version | 400 INVALID_REQUEST |
| 수정 대상이 조회 시점에 없음 | 404 POST_NOT_FOUND |
| 요청 버전 불일치 또는 커밋 시 동시 수정·삭제 충돌 | 409 CONFLICT |
| 수정 성공 | 기존과 같은 200, data는 null |

수정 후 다시 편집하려면 최신 조회 응답에서 version을 얻습니다.
서버가 버전을 관리하므로 클라이언트는 직접 증가시키거나 예상 값으로 대체하지 않습니다.
동일 제목·본문을 저장하는 요청은 변경 감지가 없어 버전을 증가시키지 않습니다.
이 요청은 실제 쓰기가 없으므로 동시 변경과 모두 성공할 수 있습니다.

기존의 version 없는 PUT 요청은 더 이상 허용하지 않습니다.
GET의 조회수 증가와 HEAD의 비증가 계약은 그대로 유지합니다.
version은 편집 충돌 검사 값이며 조회수까지 포함한 응답 전체의 캐시 검증자는 아닙니다.

## 두 단계 검사가 필요한 이유

1. `PostCommandService`가 요청 버전과 조회한 엔티티 버전을 비교합니다.
   요청이 시간상 겹치지 않아도 오래된 편집 화면의 덮어쓰기를 막습니다.
2. `Post`의 `@Version`이 실제 SQL UPDATE·DELETE의 버전 조건을 검사합니다.
   두 트랜잭션이 사전 검사를 모두 통과한 뒤 경합해도 하나의 내용 변경만 커밋됩니다.

버전을 읽어 비교하는 것만으로는 두 검사 사이의 경합을 막지 못하고,
`@Version`만으로는 매 요청이 최신 엔티티를 읽는 오래된 편집 화면을 구분하지 못합니다.
서비스의 기존 트랜잭션·JPA 변경 감지를 유지하며 별도 저장 인터페이스나 전역 잠금을 추가하지 않습니다.

버전은 JPA만 변경합니다. 클라이언트가 보낸 version을 엔티티 필드에 대입하지 않습니다.
조회수는 기존 native UPDATE로만 증가하고 일반 엔티티 UPDATE에서 제외하므로
편집 버전을 바꾸거나 오래된 엔티티의 본문 수정으로 조회수를 덮어쓰지 않습니다.

## 예외 변환과 책임

사전 버전 불일치는 기존 공통 충돌 계약인 `BaseException(GlobalErrorCode.CONFLICT)`로 전달합니다.
커밋 시 발생하는 `OptimisticLockingFailureException`도 전역 웹 핸들러가 같은 409·CONFLICT로 변환합니다.
서비스 메서드가 반환된 뒤 트랜잭션 커밋에서 발생할 수 있으므로 서비스 내부 catch에만 의존하지 않습니다.
전역 핸들러는 게시글 타입을 모르며, 회원 등 다른 도메인의 낙관적 잠금 충돌에도 재사용할 수 있습니다.

DELETE는 요청 버전을 필수로 받지 않습니다. 삭제 전 조회 이후 경합은 @Version으로 감지해 409가 가능합니다.
오래된 화면에서 보낸 삭제 의도까지 검사해야 한다면 DELETE의 예상 버전 계약을 별도로 추가해야 합니다.
이 변경은 편집 충돌 검사이며 인증·인가를 대신하지 않습니다.

## 스키마와 배포

V4가 BIGINT NOT NULL DEFAULT 0의 version과 음수 금지 제약을 추가합니다.
기존 제목·본문·조회수는 보존하고 기존 게시글 버전은 0으로 시작합니다.
기존 V1~V3 파일은 변경하지 않습니다.

버전을 갱신하지 않는 구버전 서버와 새 서버가 동시에 수정 요청을 처리하면 보장이 깨집니다.
구버전 인스턴스의 쓰기 처리를 중지하고 V4를 적용한 새 서버로 전환해야 합니다.
수정 클라이언트도 version을 전달하는 계약으로 함께 전환합니다.

## 검증

```sh
./gradlew test postgresTest spotlessCheck bootJar
```

- HTTP에서 오래된 편집 거부, 최신 버전으로 재검토 후 수정, 누락·음수·소수·미래 버전 거부.
- 조회수 증가가 version을 바꾸지 않고 본문 수정만 버전을 증가시키는지 확인.
- PostgreSQL에서 두 트랜잭션이 같은 스냅샷을 읽은 뒤 실제로 하나만 커밋하는지 확인.
- PostgreSQL HTTP 테스트에서 실제 조회 후 배리어로 두 스냅샷을 일치시키고,
  저장·커밋을 대체하지 않은 채 200 하나와 409 하나를 검증.
- 기존 V3 데이터의 제목·본문·조회수 보존, V4 버전 0과 마이그레이션 재실행 검증.
- 후속 처리 실패 시 본문과 편집 버전의 롤백 검증.

HTTP 경합 테스트의 spy는 실제 조회 이후 실행 순서만 제어합니다.
DB 변경과 버전 검사, 트랜잭션 커밋 및 예외 변환은 실제 구현을 사용합니다.

참고: [Hibernate 낙관적 잠금](https://docs.hibernate.org/orm/current/userguide/html_single/#locking-optimistic),
[Spring 낙관적 잠금 예외](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/dao/OptimisticLockingFailureException.html).
