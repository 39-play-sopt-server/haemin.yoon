# 게시글 좋아요

## API와 정책

| 요청 | 동작 | 응답 |
| --- | --- | --- |
| `PUT /posts/{postId}/likes/{memberId}` | 좋아요 상태로 설정 | 200, `data.liked=true`, `data.likeCount` |
| `DELETE /posts/{postId}/likes/{memberId}` | 좋아요 상태 해제 | 200, `data.liked=false`, `data.likeCount` |

본문은 필요하지 않습니다. 같은 PUT을 반복해도 좋아요는 한 번만 추가되고,
같은 DELETE를 반복해도 개수는 한 번만 감소합니다. 취소 후 다시 좋아요할 수도 있습니다.
다른 회원의 좋아요에는 영향을 주지 않으며 자기 게시글에도 좋아요할 수 있습니다.

```sh
curl -X PUT http://localhost:8080/posts/1/likes/2
curl -X DELETE http://localhost:8080/posts/1/likes/2
curl http://localhost:8080/posts/1
```

설정·취소 응답 예시:

```json
{"success":true,"code":"SUCCESS","message":"좋아요를 설정했습니다.","data":{"liked":true,"likeCount":3},"violations":[]}
```

게시글 목록·제목 검색·동적 필터·단건 응답에는 `likeCount`가 포함됩니다.
좋아요 변경은 조회수·게시글 편집 버전·게시글 수정일을 변경하지 않습니다.
기존 글과 새 글의 초기 좋아요 수는 0입니다. HEAD는 기존처럼 본문을 반환하지 않습니다.

회원과 게시글 ID는 양수여야 합니다. 0 이하는 400 `INVALID_LIKE_ID`, 형식 오류는
400 `INVALID_REQUEST`입니다. 회원 확인을 먼저 수행하고, 없는/탈퇴 회원은
404 `MEMBER_NOT_FOUND`, 없는 게시글은 404 `POST_NOT_FOUND`입니다.
탈퇴 회원은 설정·취소를 할 수 없으며 기존 좋아요와 개수는 유지합니다.
게시글을 삭제하면 해당 좋아요 관계도 DB 외래 키의 `ON DELETE CASCADE`로 정리합니다.
회원이나 다른 게시글은 삭제하지 않습니다.

현재는 로그인 없이 명시적인 회원 ID로 동작합니다. 인증을 도입하면 컨트롤러에서
인증된 회원 ID를 받아 Facade에 전달해야 하며, 클라이언트가 다른 회원을 지정하지 못하게
요청 경계를 변경해야 합니다. 회원 활성 여부 검사는 서비스에서 계속 수행합니다.
활성 상태 확인 후 탈퇴가 완료된 진행 중 요청은 완료될 수 있습니다.

## 다대다와 책임 분리

`Member 1 : N PostLike N : 1 Post`로 회원과 게시글의 다대다를 표현합니다.
`@ManyToMany` 컬렉션 대신 `PostLike` 연결 엔티티를 사용하여 좋아요 시각과
관계 제약을 명시하고, 거대한 좋아요 컬렉션을 읽거나 변경하지 않게 합니다.
`PostLike`는 `BaseEntity`의 시각을 사용하며 `(post_id, member_id)` 유일 제약으로
같은 회원의 중복 좋아요를 DB에서도 막습니다.

- 게시글 웹 어댑터는 HTTP·응답 DTO·좋아요 전용 OpenAPI 오류를 담당합니다.
- `PostLikeFacade`는 트랜잭션 밖에서 재시도를 조율합니다.
- `PostLikeCommandService`는 활성 회원 확인, 멱등성, 관계와 카운터 변경의 트랜잭션을 담당합니다.
- `LoadPostLikePort`·`SavePostLikePort`와 출력 어댑터는 잠금·관계 저장·개수 갱신을 담당합니다.
- 회원 도메인은 활성 회원 조회를 계속 소유하며, 전역 예외 핸들러에는 좋아요 분기를 추가하지 않습니다.

`posts.like_count`는 조회 비용을 줄이기 위한 저장된 집계값입니다.
목록을 읽을 때 각 글의 좋아요를 COUNT하거나 컬렉션을 fetch하지 않습니다.
관계 변경과 카운터의 원자적 `+1/-1`은 같은 트랜잭션에서 커밋·롤백됩니다.
중복 설정과 이미 취소된 요청에서는 카운터를 변경하지 않습니다.
음수는 CHECK 제약으로도 방어하며, ORM의 본문 수정은 `like_count`를 덮어쓰지 않습니다.

## 데드락 예방과 복구

좋아요 행을 먼저 INSERT하면 PostgreSQL의 게시글 외래 키 검사에서 부모 행에
KEY SHARE 잠금을 취득할 수 있습니다. 이후 부모를 `FOR UPDATE`로 잠그는 구현에서는
동시 요청의 잠금 승격이 충돌할 수 있고, 관계를 먼저 잠그는 취소 경로와 부모부터
잠그는 삭제 경로가 섞이면 역순 접근으로 순환 대기가 생길 수 있습니다.
비키 컬럼의 일반 UPDATE가 얻는 NO KEY UPDATE 잠금은 KEY SHARE와 호환되므로
단순한 INSERT 뒤 카운터 UPDATE 자체가 항상 데드락을 만든다는 의미는 아닙니다.
전체 쓰기 경로의 잠금 순서를 함께 고려해야 합니다.

이번 구현은 설정·취소 모두 다음 순서를 지킵니다.

1. 활성 회원을 일반 조회합니다. 회원 행은 배타 잠금하지 않습니다.
2. `SELECT id FROM posts WHERE id = ? FOR UPDATE`로 게시글 하나만 먼저 잠급니다.
   작성자 JOIN에 잠금을 전파하지 않도록 잠금 쿼리를 분리합니다.
3. 잠금을 취득한 뒤 좋아요 관계를 검사·추가하거나 삭제합니다.
4. 실제 관계가 바뀐 경우에만 카운터를 갱신하고 커밋합니다.

같은 게시글의 변경은 DB에서 순서대로 처리되며, 여러 서버 인스턴스에서도 동일하게 작동합니다.
게시글 삭제도 부모 행을 삭제하면서 잠근 뒤 DB cascade로 좋아요 행을 삭제하므로 같은 순서입니다.
좋아요 컬렉션을 먼저 지우는 ORM cascade는 추가하지 않습니다.

외부 SQL이나 향후 다른 쓰기 경로까지 잠금 순서를 강제할 수는 없으므로 복구도 제공합니다.
Spring의 `PessimisticLockingFailureException` 계열과 `QueryTimeoutException`만
최초 시도 포함 최대 3회 실행합니다. PostgreSQL 영속성 어댑터는 부모 잠금 전에
`SET LOCAL lock_timeout = '2s'`를 적용합니다. 이후 관계 INSERT/DELETE, 카운터 갱신의
암묵적 잠금을 포함해 각 잠금 획득의 대기를 2초로 제한합니다. 따라서 부모 잠금을 잡은 뒤
좋아요 행에서 기다리는 경우에도 시간 초과가 발생하고 롤백·재시도합니다.
설정은 커밋·롤백 때 복원되므로 커넥션 풀의 다음 사용자에게 전파되지 않습니다.
PostgreSQL 전용 SQL은 게시글 영속성 어댑터가 소유하며 H2에는 실행하지 않습니다.
기존 게시글 잠금 조회의 JPA 2초 실행 제한도 유지합니다.
이 제한은 잠금 획득별 제한이며 요청 전체의 2초 완료를 보장하지 않습니다.
시도 사이에는 10~30ms, 다음에는 20~60ms의 임의 지연을 둡니다.
회원·게시글 없음, 무결성 위반 등 다른 실패는 자동 재시도하지 않습니다.

Facade의 `Propagation.NEVER`는 외부 트랜잭션에서의 호출을 거부합니다.
각 서비스 호출이 별도 트랜잭션을 시작하고, 실패한 트랜잭션의 롤백이 끝난 뒤
새 트랜잭션에서 전체 작업을 다시 실행합니다. 동일 트랜잭션 내부에서 실패한 SQL만 재실행하지 않습니다.
3회 실패 시 원인을 서버 로그에 기록하고 503 `POST_LIKE_BUSY`를 반환합니다.
클라이언트는 동일한 PUT 또는 DELETE를 다시 보낼 수 있습니다.

## 검증

```sh
./gradlew test postgresTest spotlessCheck bootJar
```

- `PostLikeHttpTest`: 반복 설정·취소, 재설정, 회원별 독립성, 다대다 관계, 조회 응답,
  메타데이터 보존, 비활성/없는 회원과 글, 입력 검증, 삭제 정리, OpenAPI.
- `PostLikeFacadeTest`: 잠금 오류만 재시도, 최대 횟수, 일반 오류 재시도 제외.
- `PostLikeConcurrencyTest`: 실제 PostgreSQL에서 여러 회원의 동시 설정·취소,
  같은 회원의 중복·상반 요청, 조회수 증가와의 경합, 게시글 삭제 경합,
  관계와 카운터의 일치, 유일·외래 키·음수 제약을 확인합니다.
- 카운터 갱신 직후 실패를 주입해 관계와 카운터의 롤백 및 재시도 정합성을 검사합니다.
- 별도 연결이 관계 → 부모 순서로 잠그게 하여 실제 SQLSTATE 40P01 데드락을 발생시킵니다.
  실제 잠금 예외를 관찰하고 재시도 전후 DB 트랜잭션 ID가 다르며 최종 취소가 성공함을 확인합니다.
- 부모 행을 다른 연결에서 계속 잠근 상황에서 시간 초과·재시도 소진·503 코드도 확인합니다.
- 좋아요 행만 다른 연결에서 잠그고 부모 잠금 이후 DELETE가 대기하도록 재현합니다.
  3회 실패의 트랜잭션 ID 분리, 관계·개수 보존, 부모 잠금 해제와 오류 코드를 확인합니다.
  첫 관계 행 시간 초과 이후 차단을 해제하면 새 트랜잭션에서 취소가 성공하는 경우도 확인합니다.

## 한계와 확장 지점

인기 게시글 하나의 쓰기는 해당 행에서 직렬화됩니다. 현재 요구사항에서는 읽기 비용과
정확한 카운터를 우선하며, 운영 규모 처리량·대기 시간 검증은 별도로 필요합니다.
실제 경합이 병목이 된다면 분산 카운터나 이벤트 집계를 검토할 수 있지만,
이때는 개수의 지연 반영과 중복 이벤트 처리 정책도 함께 설계해야 합니다.

응답의 개수는 처리 시점의 값이며 다른 회원의 요청으로 즉시 바뀔 수 있습니다.
같은 회원이 PUT과 DELETE를 동시에 보내면 서버에서 처리된 순서가 결과를 결정합니다.
클라이언트의 마지막 클릭 의도를 보장하려면 게시글별 요청을 순서대로 보내거나
진행 중 요청이 끝난 후 마지막 희망 상태를 다시 전송해야 합니다. 토글 API는 제공하지 않습니다.

좋아요 목록을 추가한다면 연결 엔티티를 기준으로 별도 커서 조회를 추가하면 됩니다.
여러 게시글을 한 트랜잭션에서 변경하는 기능을 추가한다면 게시글 ID 오름차순 등
모든 경로의 잠금 순서를 통일해야 합니다. 현재 Facade의 단건 트랜잭션을 그대로 묶어 호출하지 않습니다.
탈퇴 시 좋아요를 제거하는 정책으로 바뀐다면 회원 삭제 유스케이스와 집계 갱신을 함께 설계해야 합니다.

관계 테이블이나 카운터를 운영 SQL로 직접 변경하면 집계가 어긋날 수 있습니다.
정합성 확인이 필요하면 다음 조회로 차이를 찾을 수 있습니다. 이번 구현은 자동 보정 작업을 추가하지 않습니다.

```sql
SELECT p.id, p.like_count, COUNT(l.id) AS actual_count
FROM posts p LEFT JOIN post_likes l ON l.post_id = p.id
GROUP BY p.id, p.like_count
HAVING p.like_count <> COUNT(l.id);
```

참고: [PostgreSQL 잠금과 데드락](https://www.postgresql.org/docs/current/explicit-locking.html),
[Spring 트랜잭션 전파](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html).
